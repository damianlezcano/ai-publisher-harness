## ROOT-CAUSE PASS: REAL `embedding_persist_failed` WAS A SCOPED-QUERY PARAMETER COLLISION (2026-09-07)


- **Starting tree:** `8415c61` (one uncommitted `runtime_gate.rs` test file + the prior `SQLITE_BUSY` regression test already in `lib.rs`). A fresh Fedora one-file AppImage run still reported `embedding_failure_class=embedding_persist_failed` (`lexical_ready=1`, `embeddings_created=0`, `embeddings_reused=0`, `ready=0`, `errors=1`) while the K6 summary still finished (`remote_calls=1`). The previous busy_timeout pass was proven structurally correct but had targeted the WRONG path: no test ever exercised the scoped (`index_embeddings_for_materials` with a non-empty material list) embedding persistence against a real provider, so the actual failure hid in a query that only the accepted-turn batch path runs.
- **Exact root cause (proven, reproduced, not guessed):** `KnowledgeStore::index_embeddings_for_materials` builds a *scoped* `SELECT` for the accepted batch: the material `IN (...)` placeholder is a bare `?` (auto-numbered to parameter index 1) while the generation selector uses an explicit `?1` — so the two **collide on index 1**. SQLite reports the statement declares **one** parameter, but the code bound **two** values (`generation_id` + each `material_id`). `query_map` failed with *"Incorrect number of bindings supplied: this statement uses 1, and 2 are supplied"*, surfaced as `KnowledgeError::Sql`, which `embedding_index_failure_state` collapses to `SemanticProviderState::EmbeddingPersistFailed` — the exact symptom. Verified independently against a raw SQLite connection (`python3` sqlite3) and confirmed by a failing-then-passing regression test.
- **Fix (bounded, single function):** the scoped query now binds material ids first (`?1..?N`) and the generation selector last at an explicit index `?{N+1}`, with the bound values in the same order, so every declared parameter is bound exactly once. The non-scoped (full-repair) path already used only `?1` and is unchanged.
- **Observability (section E):** added `EmbeddingPersistClass` (`sqlite_busy`, `sqlite_locked`, `transaction_begin_failed`, `transaction_commit_failed`, `statement_prepare_failed`, `constraint_failed`, `vector_serialization_failed`, `vector_dimension_invalid`, `io_failed`, `db_corrupt`, `other_storage_failure`) and an `EmbeddingPersistFailure { stage, class, sqlite_code }` classifier. `index_embeddings_for_materials` now *preserves* the actual `rusqlite` error at the transaction/insert/commit stages instead of collapsing to a bare `EmbeddingPersistFailed`, and the accepted-batch boundary emits a sanitized `[knowledge][embedding] stage=… failure_class=… sqlite_code=…` line (primary SQLite code only; never SQL text, a path, a vector, or a document body). The existing `busy_timeout=5000ms` stays.
- **Material final-state + processing-card terminal UX (sections H/I):** the operation still reaches a truthful terminal `completed` state; the frontend processing card now renders a compact terminal state instead of a forever-"Procesando" title — `"1 archivo procesado"` when `embeddingCompleted >= total`, and `"1 archivo procesado con problemas"` + `"Indexación semántica no disponible"` when semantic indexing failed (`embeddingCompleted < total`). The live counters/title only render while the operation is genuinely in flight.
- **Knowledge telemetry survival (section J):** the K6 summary route now emits `record_knowledge` (`SessionKnowledgeMetrics`) with the corpus/index facts (material count, corpus bytes/chars/est-tokens, semantic state) it always knows, instead of leaving the Conversation Details "Knowledge" section uniformly "No disponible". Per-turn retrieval/evidence/context-reduction/preparation fields that a summary turn genuinely lacks were made `Option<…>` (`null` → "No disponible") rather than an invented zero.
